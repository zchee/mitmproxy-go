### 1.3.1 Starlark `concurrent` design

1. *Spelling and hook name.* go.starlark.net has no decorator syntax: its scanner has no `@` token (`go.starlark.net@v0.0.0-20260930220527-d7438c5a85ac` `syntax/scan.go`) and `doc/spec.md` has no decorator production. `concurrent` is therefore a predeclared builtin function that takes a function and returns a wrapper value, written at module top level as `def _request(flow): ...` followed by `request = concurrent(_request)`. `FileOptions.GlobalReassign` stays off (the zero value, `syntax/options.go:28`), so `def request(flow): ...` followed by `request = concurrent(request)` fails to resolve, as in standard Starlark. The hook name comes from the global binding, not from the function, because `Function.Name()` returns the `def` name, `_request` (`starlark/value.go:759`): after `Program.Init` the loader walks the module globals and checks every global whose value is a `concurrent` wrapper under its binding name (rule 6), and the dispatcher looks up the same binding name in the frozen instance (rule 2). **Documented deviation** (§9, `docs/compat.md`): the `@concurrent` line of a Python script becomes this assignment. The wrapper implements `starlark.Callable` (`starlark/value.go:182-186`) so that a direct Starlark call of it, such as `request(flow)` from another hook or from top-level code, fails with the port's own text `concurrent(<fn>) cannot be called directly; it runs only when invoked as a hook`, where `<fn>` is the wrapped function's `Function.Name()` (a direct call can happen during module init, before the binding walk of rule 6 has named the wrapper); without `Callable` the user would see the interpreter's `invalid call of non-function (concurrent)` (`starlark/eval.go:1201`). **Documented deviation** (§9, `docs/compat.md`): upstream's wrapper is an `async def` (`concurrent.py:18-30`), so a direct Python call returns a coroutine that is never awaited and the handler never runs; Starlark has no coroutine value to return.
2. *Second module instance.* A frozen snapshot of the live globals cannot be built: a function reads its module's globals slice directly (`go.starlark.net@v0.0.0-20260930220527-d7438c5a85ac` `starlark/interp.go:640-641`, `fn.module.globals[arg]`), `Module` has no setter (`starlark/value.go:729-734`), and `StringDict.Freeze` freezes values in place (`starlark/eval.go:177-181`). Each script that binds at least one `concurrent` wrapper to a global therefore gets a second module instance from a second `Program.Init` run (`starlark/eval.go:436-444` builds fresh globals on every call), frozen with `StringDict.Freeze` right after init. Concurrent handlers are taken from that frozen instance; a frozen module may be called from several threads at once (`doc/spec.md:1390-1393`). Top-level code runs twice per load (and per reload). Each instance has its own predeclared object graph: `Program.Init` takes the predeclared dictionary as an argument (`starlark/eval.go:436-444`) and a function reads predeclared names from its own module (`starlark/interp.go:649-651`), so the second `Init` is passed a fresh `ctx` and fresh objects behind it (`ctx.options`, `ctx.master`, `ctx.log`), built for that instance and switched to worker mode after init (rule 4). `StringDict.Freeze` calls `Freeze` on every global value (`starlark/eval.go:177-181`), which reaches a predeclared object when a global aliases it, as in `o = ctx.options`. These objects keep `Freeze` as a no-op, because they hold no Starlark state of their own: what they read and write is Go state shared by both instances (the options manager, the command manager, the log), and that shared state is internally synchronised (rule 4 says how a worker reaches it). A real freeze would make `o.x = 1` fail in a worker although the same write through `ctx.options` is meant to work. **Documented deviation** (§9, `docs/compat.md`): module-level mutable state is not shared between a `concurrent` handler and the main-thread hooks; the handler sees the globals as they were after init, and writes to them raise "cannot insert into frozen hash table" (`starlark/hashtable.go:79,334`).
3. *Workers.* Each invocation runs on its own goroutine with its own `starlark.Thread`, bounded by a semaphore of min(32, GOMAXPROCS + 4) per script, the size of CPython's default executor that upstream's `run_in_executor(None, ...)` uses (`concurrent.py:30`; CPython 3.14.6 `concurrent/futures/thread.py:181`).
4. *Release and reacquire.* The worker call is built on §3.1 rule 4 (`addon.Concurrent`): the flow's hook chain waits, the dispatch lock is released while the handler runs and reacquired with a fresh frame for the merge-back. The flow is **not** intercepted, because upstream only awaits the executor (`concurrent.py:18-30`) and an intercept would let mitmweb or the console resume a flow whose merge-back is still pending. Code reached from a worker never touches shared state outside the dispatch lock. The second instance's predeclared graph (rule 2) has two modes. It is in **direct** mode while that instance's top-level code runs during its `Program.Init`, which happens on the loading goroutine under the dispatch lock, so a top-level `ctx.log("init")` there is logged at once instead of waiting on `master.Do`, which would deadlock. It is switched to **worker** mode under the dispatch lock after `StringDict.Freeze` and before the instance is handed to the dispatcher, so no worker goroutine can start against it in direct mode (the goroutine start orders the switch before the worker's first access). The main instance's graph is always in direct mode, because its code runs only inside the dispatch domain. In worker mode, attribute access does not need to know which goroutine or which worker it runs on, which it could not learn anyway (`HasAttrs.Attr` and `HasSetField.SetField` receive no `*Thread`, `starlark/value.go:367,385`, and up to min(32, GOMAXPROCS + 4) workers share the instance, rule 3): a `ctx.options` read loads the latest options snapshot from an `atomic.Pointer`; a snapshot is never modified after it is published; it is published once when the script is loaded and then by a subscriber registered with `options.Manager.Subscribe` (`go:options/manager.go:181` on main), which runs where the change is made, inside the dispatch domain (§3.1 rule 5), after every change and again after a rollback (`go:options/manager.go:176-180`); list-valued options are handed to Starlark as frozen values or as per-read copies, so two workers never share a mutable list. `ctx.options` writes, `ctx.master.commands.call` and `ctx.log` run through `master.Do` (§3.1 rule 5; `go:master/master.go:90` on main). Blocking builtins (`ctx.sleep`, `ctx.http_get`) park only that goroutine and never touch the lock. A worker's read of an option that a `master.Do` callback changes while the handler runs therefore returns the old or the new value. A visible consequence: a worker's `ctx.log` line reaches `add_log` and `eventstore` when the dispatch lock is next free, not at the moment of the call. *Reload and remove*: hot reload and `remove` never wait for in-flight workers while they hold the dispatch lock, because a worker blocked in `master.Do` (for `ctx.log`, say) would then wait for that lock forever. They mark the script's frozen instance retired and fire `done` at once, as upstream's `remove` takes the addon out of the chain and invokes `done` without waiting for anything (`py:mitmproxy/addonmanager.py:206-220`); no new invocation starts on a retired instance, and in-flight workers finish against it, its semaphore and its predeclared graph. A finished worker's merge-back (rule 5) runs as usual while its flow's hook chain is still waiting for it, as upstream's chain keeps awaiting `run_in_executor` across a reload (`concurrent.py:30`); it is dropped only when that wait has already ended because the connection closed and the stream's context was cancelled.
5. *Copy and merge-back.* The handler receives a deep copy of the flow (a Go-side clone wrapped as a fresh Starlark value); a snapshot of the copy's state is kept. On return, under the lock, each state field the handler changed relative to the snapshot is written to the live flow, and fields it did not change keep the live value (upstream shares one object, so the last writer wins per field; a full overwrite would discard concurrent `master.Do` edits). The merged fields are every key of the flow state (`py:mitmproxy/flow.py:143-159` plus the per-type keys, e.g. `py:mitmproxy/http.py:1237-1239`) except `version`, `type`, `id`, `timestamp_created` and the two connections: `error`, `is_replay`, `marked`, `metadata`, `comment`, `backup`, the HTTP `request`/`response`, the `websocket` data (`messages`, `closed_by_client`, `close_code`, `close_reason`, `timestamp_end`, `py:mitmproxy/websocket.py:161-175`), the DNS `request`/`response`, and the `messages` lists of TCP and UDP flows (`py:mitmproxy/tcp.py:58-62`); `intercepted` is handled by the replayed actions below. Message lists merge by index: entries that existed at copy time are taken from the copy, entries the live flow gained while the handler ran (the other WebSocket relay direction keeps appending, §3.1) are kept. `flow.intercept()`, `flow.resume()` and `flow.kill()` (which sets `error`) called on the copy are recorded as actions and replayed on the live flow under the lock in call order. Connection objects (`client_conn`, `server_conn`) are goroutine-owned (§3.1 rule 6), so the copy carries a read-only snapshot of both taken at copy time; a write to them from the handler raises an error, and they are never merged back (**documented deviation**: upstream's handler shares the live connection objects).
6. *Eligible hooks.* A `concurrent` wrapper is accepted when its binding name (rule 1) is one of the 23 hooks whose argument is a flow (the HTTP, WebSocket, TCP, UDP and DNS flow hooks). Bound to `on_load` or `configure`, it fails the script load with upstream's text `Concurrent decorator not supported for '<name>' method.` (`concurrent.py:13-16`), where `<name>` is the binding name. The other 21 hooks take no flow, or something other than a single flow (`tls_clienthello`, `next_layer`, `server_connect`, `client_connected` and the rest of the connection, TLS, QUIC and SOCKS5 hooks, plus `update`, `add_log`, `running`, `done`): they always run inline on the main thread, and a wrapper bound to one of them fails the load with the same text (**documented deviation**: upstream accepts them, `concurrent.py:13`). A wrapper bound to a global that is not a hook name fails the load with the same text, as upstream's check does for any other function name (`concurrent.py:13`).
7. *`script.run`.* Go's `script.run` command is a synchronous invocation of the script module only, exactly as upstream's (`py:mitmproxy/addons/script.py:180-188`: `configure`, `running`, then `eventsequence.iterate` over each flow, every event through `invoke_addon_sync(mod, evt)`, which visits the module and its own nested `addons` through `_iter_hooks` and `traverse`, `py:mitmproxy/addonmanager.py:110-117,243-262,278`, so no hook outside the script module and the nested `addons` it defines is invoked). It initialises the module once with `Program.Init` and builds no frozen second instance, because its `concurrent` handlers are never run. The eligibility walk of rules 1 and 6 runs on that module init, as on a `-s` load, and a failure takes upstream's load-error path: upstream's check runs when the decorator is applied during module execution inside `load_script` (`py:mitmproxy/addons/script.py:23-57`), the exception is caught there (`:51,54`) and logged by `script_error_handler` as `error in script <path>` with the error (`:60-71`), `load_script` returns `None`, and `script.run` invokes no event (`:178-179`); the port logs the same line and invokes no event. Its invoker checks each handler before calling it, whatever the dispatch depth: a `concurrent` wrapper is rejected with upstream's error `Async handler <hook> (<script>) cannot be called from sync context` (`py:mitmproxy/addonmanager.py:279-282`), where the port prints the script's path as `<script>`; upstream prints the module's repr there (`{addon}` at `:281`, such as `<module '__mitmproxy_script__.x' from '/path/x.py'>`), which has no Starlark counterpart (**documented deviation**). The first error ends the whole run, the remaining events and flows included, because upstream wraps the loop in one `safecall` (`script.py:180`), which logs `Addon error: <message>` (`addonmanager.py:56-59`). No other path reaches a flow hook synchronously: upstream's other synchronous invocations fire `update` (`py:mitmproxy/addons/core.py:62-238`, `view.py:400,413`, `clientplayback.py:263,287`, `serverplayback.py:155,171`, `comment.py:19`) or `configure`, `load`, `running` and `done` (`py:mitmproxy/addonmanager.py:139,146,189,220`, `script.py:124-131,229`), none of which the port lets a `concurrent` wrapper serve (rule 6), and the port adds no synchronous flow-hook invocation. `addon.Concurrent` keeps its own depth rule for Go addons (§3.1 rule 4).

Go's `crypto/tls` runs ECH processing before `GetConfigForClient`; without the origin's ECH key the proxy sees only the outer `public_name` SNI, so clients attempting ECH to the proxy's leaf certificate fail unless the `strip_ech` option (default true, implemented by `strip_dns_https_records` in P4) has cleared the `ech` parameter of the HTTPS records they resolved through the proxy.

## 2. RALPLAN-DR summary

### Principles

1. **Pr1 Bytes in, same bytes out.** Anything the proxy does not deliberately change is forwarded unchanged at the fidelity scope defined in §1.2: HTTP/1 header case and order, HTTP/2 and HTTP/3 header lists and pseudo-header order, WebSocket uncompressed fragment layout, control frames, close codes. Normalisation only happens through an explicit option.
2. **Pr2 Upstream compatibility is a tested contract.** Flow files, CA layout, filter language, option names and precedence, hook names, mode specs and the mitmweb API are verified against upstream fixtures copied into `testdata/` and against the pinned Python mitmproxy in differential tests.
3. **Pr3 Hybrid, not dogmatic.** Pure parsers are sans-I/O with vector tests; anything that terminates TLS over TCP or QUIC uses the native `net.Conn`/`quic.Conn` Go APIs; protocol state machines are goroutine-owned.
4. **Pr4 Pure Go by default; native pieces are reused, not rebuilt.** Signed or kernel-adjacent components (macOS Network Extension, WinDivert driver) come from upstream release artifacts pinned by version and SHA-256.
5. **Pr5 From P1 on, every phase leaves a runnable mitmdump.** P0 is the only phase without a binary and is kept to the data model and registries that P1 cannot start without; afterwards nothing merges without the phase's acceptance tests.

### Decision drivers (top 3)

1. **D1 Asset compatibility**: users keep their `~/.mitmproxy` CA, `.mitm` dumps (v18 and newer), filter expressions, `config.yaml` and the mitmweb UI.
2. **D2 Maintainability on Go 1.27+**: std first; a third-party package when it is meaningfully better or std has no equivalent (the project's own rule); the five version-sensitive integrations (netstack, h2 framing, h3 framing, DNS codec, YAML codec) sit behind one adapter package each so drift is local.
3. **D3 Delivery-risk control**: ~48k lines of Python plus the Rust surface is ported in phases with upstream test vectors as the regression net, and the hardest native pieces (local mode) are isolated and feature-flagged.

### Viable options

| Option | Summary | Pros | Cons |
|---|---|---|---|
| **O1 (chosen)** Hybrid core, full wire fidelity, full compatibility | Own HTTP/1 parser, own h2/h3 endpoints on x/net Framer and quic-go streams, native TLS/QUIC I/O, upstream formats and APIs | Satisfies D1 fully; parsers reuse upstream vectors; h2/h3/WS fidelity equal to upstream; Go-native I/O | Largest code volume; two implementation styles to keep consistent; HTTP/2 and HTTP/3 state machines (SETTINGS, windows, stream states, GOAWAY, QPACK) are written here rather than borrowed; a lock discipline the type system cannot enforce (mitigated by the epoch-checked token, §3.1) |
| O2 std `net/http`-based proxy (goproxy-style), data-level compatibility only | Use `http.Server`/`Transport` with `Protocols`, keep flow files and CA compatible, redesign options/API | Fastest to ship; least code | Loses header case/order, non-token header names rejected, `Expect: 100-continue` handled by std, h2 re-encoded (map order); mitmweb React build unusable without a new API; violates Pr1 |
| O3 Faithful sans-I/O port | `Layer` state machines yielding `Command`s via `iter.Seq`, a server loop driving I/O | Upstream playbook tests port almost 1:1; deterministic tests | `crypto/tls` over TCP and quic-go are I/O-driven (no memory-BIO mode), so the TLS and QUIC layers need `net.Pipe`-style adapters and goroutines anyway (`xnet:http2.Framer` and `crypto/tls.QUICConn` would work sans-I/O); highest code volume; unusual for Go contributors |
| O4 Fork `github.com/lqqyt2423/go-mitmproxy` (MIT, v1.9.3, mitmproxy-compatible CA) | Start from an existing Go MITM proxy and add compatibility | Working HTTP/1, h2 (std) and WebSocket (gorilla) on day one | Built on std `net/http` and `x/net/http2` Server/Transport, so it has the O2 fidelity losses by construction; no flow format, filter, options, hooks or mitmweb compatibility; divergent architecture would be replaced piece by piece |

**Invalidation rationale**: O2 and O4 contradict driver D1 (mitmweb API, byte fidelity) and principle Pr1; O3 is rejected because the two I/O-bound libraries force adapters at the TLS and QUIC boundaries, which removes the main benefit of sans-I/O while keeping its cost. O1 keeps O3's benefit where it is cheap (pure parsers) and O2's benefit where it matters (native I/O). An actor-goroutine dispatch model was considered as a variant of O1 and rejected because the user fixed hooks on the stream goroutine; §3.1 rules 3 and 7 recover most of the actor model's safety (epoch-checked token, non-blocking frontend edges).

## 3. Target architecture

### 3.1 Concurrency and layering model

```
listener (TCP / UDP 4-tuple demux / QUIC / netstack forwarder / local-mode IPC)
  └─ proxy.ConnectionHandler            one goroutine per client connection; owns client Conn, server Conns, watchdog, pool
       ├─ layer.NextLayer sniff         recording conn buffers until the sniff decision (py:mitmproxy/addons/next_layer.py)
       ├─ modes.* top layer             regular/reverse/upstream/transparent/socks5/dns (py:mitmproxy/proxy/layers/modes.py)
       ├─ tls.ClientTLS / ServerTLS     crypto/tls over net.Conn; full ClientHello recorded (may span records) and replayed
       ├─ http.Layer                    HTTP/1 (own parser) | HTTP/2 (own endpoint per side on Framer+hpack) | HTTP/3 (own frames on quic.Stream + qpack)
       │    └─ http.Stream              one goroutine per request/response pair; hooks dispatched under the dispatch lock
       ├─ websocket.Layer               after 101; two relay goroutines (client→server, server→client) + inject channel
       ├─ tcp.Layer / udp.Layer         raw relay with message capture, inject channel, `ignore` fast path (TCP layer lands in P1)
       └─ dns.Layer                     request/response matching by ID; resolver addon answers when no upstream
```

**Hook dispatch domain** (mirrors upstream's single event loop where it matters):

1. `addon.Manager.Hook(ctx, hook)` takes one process-wide dispatch mutex, runs the addon chain on the **calling stream goroutine**, fires the `update` hook with the flow after every flow hook (`py:mitmproxy/addonmanager.py:232-241`), then releases the lock. All addon-shared state (`view` store, `serverplayback` flow map, `clientplayback` queue, `stickycookie` jar, `eventstore`, `save` writer, `intercept`, every Starlark module) is therefore accessed single-threaded, exactly as upstream guarantees.
2. The intercept wait (`flow.WaitForResume`) runs **after** the lock is released, and the connection watchdog is disarmed while a hook runs or a flow is intercepted (`py:mitmproxy/proxy/mode_servers.py:69-75`, `py:mitmproxy/proxy/server.py:79-89`).
3. **Re-entrancy token with epoch.** Go mutexes are not re-entrant, so every hook and command API takes a `context.Context` carrying a pointer to the current *dispatch frame*; the frame is valid only while `frame.epoch == manager.epoch`. Commands that fire `update` or `trigger` re-enter through a valid frame instead of re-locking. A goroutine spawned inside a hook inherits a frame that becomes stale as soon as the lock is released, so any later use is detected (test builds panic on a stale frame; release builds return an error).
4. `addon.Concurrent(ctx, fn)` is allowed only at dispatch depth 1 and not inside `load`, `configure`, the `done` of `remove`/`clear` or a command (upstream raises "cannot be called from sync context" for an async handler dispatched through `invoke_addon_sync` or `trigger`, `py:mitmproxy/addonmanager.py:276-283`); it bumps the epoch, releases the lock around `fn` while that flow's hook chain waits, and opens a fresh frame when it reacquires. Addons that block on I/O (`dns_resolver`, LDAP `proxyauth`) use it.
5. Goroutines outside hooks (mitmweb handlers, the console loop, the script reloader, OTel) mutate flows only through `master.Do(ctx, func(ctx context.Context) error) error`, which takes the dispatch lock and hands the callback a valid frame so that `options.Set` (fires `configure`) or `flow.Resume` (fires `update`) inside the callback re-enter instead of deadlocking.
6. Protocol state machines (h1 stream, h2/h3 connection, WebSocket, TCP/UDP relay, netstack) are goroutine-owned and lock-free; they touch flow objects only before and after a dispatch.
7. **Code running under the dispatch lock never blocks on a consumer outside it.** Hook-to-frontend notifications go through non-blocking paths: each mitmweb `/updates` client has a bounded queue (1,024 messages) and is closed with 1011 on overflow; the console keeps a coalescing dirty flag that a `tea.Cmd` goroutine drains with `tea.Program.Send` (never called under the lock, because `Send` blocks on an unbuffered channel); frontends call `master.Do` only from `tea.Cmd` goroutines or HTTP handler goroutines, never from inside the bubbletea `Update` function.
8. **Lock order**: dispatch lock → per-flow mutex, never the reverse; `CertStore` and the option registry's read path have their own mutexes because `GetCertificate` and `GetConfigForClient` run outside dispatch.

**Other model rules**

- **Server connection pool** is **per client connection**, as upstream's `HttpLayer` holds it (`py:mitmproxy/proxy/layers/http/__init__.py:921-946`), keyed on (address, tls, via, transport_protocol) plus SNI as a documented stricter deviation; establishment is single-flight so concurrent stream goroutines wait for a connection that is still being opened; when the client speaks h2 and the first established upstream connection is not h2, the remaining waiters re-dial with `reuse=false` instead of joining (`:1178-1188`); `connection_strategy` eager/lazy honoured.
- **Half-close**: a `closeWriter` interface (`CloseWrite() error`) implemented by the recording conn, gonet conns and the TCP relay; for `*tls.Conn` the proxy sends `close_notify` via `tls.Conn.CloseWrite` (only after the handshake) **and then** `CloseWrite` on the underlying TCP conn so a FIN follows, because upstream half-closes TLS with a bare FIN (`py:mitmproxy/proxy/layers/tls.py:460-466` leaves TLS shutdown to the transport close); every relay test asserts both directions close cleanly with goleak.
- **Buffered-byte handover** at every layer transition goes through the recording conn's replay: CONNECT → TLS, TLS → raw TCP on `ignore_connection`, 101 → WebSocket (`gows:WithBuffered`), h2c prior-knowledge preface, SOCKS5 → next layer.
- **Timeouts**: `tcp_timeout` default 600 s, UDP 20 s (`py:mitmproxy/proxy/server.py:47`); the watchdog is a per-connection idle timer disarmed per rule 2.
- **UDP flows**: one `UDPFlow` abstraction (a virtual `net.PacketConn` per 4-tuple with no-op `SetReadBuffer`/`SetWriteBuffer`) is shared by the UDP socket demux, the netstack UDP forwarder and the macOS per-flow IPC; QUIC runs one `quic.Transport` on that virtual conn per flow, which is how datagrams buffered during ClientHello sniffing (a Go 1.27 client's X25519MLKEM768 hello spans two Initials) are replayed in order to quic-go or to the raw passthrough; connection migration is unsupported, as upstream; proven by the P4 spike.
- **TLS ordering**: the client-side layer records bytes until the whole ClientHello handshake message has arrived (it may span several records, `py:mitmproxy/proxy/layers/tls.py:32-71` `handshake_record_contents`/`get_client_hello`), fires `tls_clienthello`, then either replays the buffer into a raw TCP relay (`ignore_connection`, `tcp.TCPLayer(ignore=True)` upstream at `:600`) or starts server TLS first when `ClientHelloData.establish_server_tls_first` is set (`py:mitmproxy/tls.py:127`; `tlsconfig` sets it to `server.tls and connection_strategy == "eager"`, `py:mitmproxy/addons/tlsconfig.py:204-208`); a failed server handshake is logged and client TLS continues (`py:mitmproxy/proxy/layers/tls.py:606-617`). **ALPN** (`py:mitmproxy/addons/tlsconfig.py:92-112,254-262,293-302`): for a secure web proxy (layer stack exactly `[HttpProxy, TLS]`, i.e. a client that speaks TLS to the proxy itself) the preset client-side protocol is forced to `http/1.1` (`:257-260`), because CONNECT over HTTP/2 is not supported (upstream's comment at `:254-256`); otherwise the preset is `client_conn.alpn` when it is already set on the client connection (by an addon in `tls_clienthello` or by a prior layer, `:262`); a preset, forced or not, is returned when the client offers it, else no protocol (`:97-101`), so a client that offers only `h2` to a secure web proxy gets no ALPN and Go leaves `NextProtos` empty instead of `["http/1.1"]`; otherwise the server's negotiated protocol is returned when offered; if the server refused ALPN (`server_alpn == b""`) the client gets no protocol either; otherwise the first client offer that is in `HTTP_ALPNS` (h2 only when `http2` is on) is chosen, else none. The server-side offer, when no addon has set one, mirrors the client's offers, dropping `h2` when `http2` is off (`:293-303`); a client that sent no ALPN extension, or a client without TLS, gets an empty upstream offer, so no ALPN extension is sent to the server (`:304-310`). `GetConfigForClient` sets `NextProtos` to exactly that single protocol or leaves it empty, because Go otherwise aborts with `no_application_protocol` where OpenSSL continues without ALPN. Until the h2 layer lands (P3), P1 forces `http2=false` semantics on both sides (only HTTP/1 ALPNs offered and selected) so h2-capable clients keep working.
- **Message injection** (`MessageInjected`) uses a per-layer channel selected alongside the relay reads.
- **Flow objects** carry a per-flow mutex only for field-level consistency between the stream goroutine and `master.Do` callers; cross-flow invariants are the dispatch domain's job.

confirmed by the user): the connection window is returned when data is read off the socket; a stream's window is returned when the stream **consumes** the data, which means: for a streamed message (`stream_large_bodies`, `py:mitmproxy/proxy/layers/http/__init__.py:631-649`), the bytes have been written to the downstream peer's socket, and bytes that have left the receive buffer but still sit in the opposite endpoint's send buffer (`BufferedH2Connection` semantics, below) are still charged to the same Σ counter; for a message buffered for its hooks, the bytes have been appended to the flow's body buffer, which is the flow's content and is bounded by `stream_large_bodies`/`body_size_limit` exactly as on HTTP/1 (`:568-650`), not by this budget (counting only the downstream write there would deadlock every buffered body larger than its stream window, because nothing is sent downstream before the `response` hook); a per-connection budget of 128 MiB bounds the **sum of granted (unconsumed) stream windows**: 100 MiB is reserved for the 100 initial windows, and a stream may grow beyond 1 MiB (up to 16 MiB) only by drawing on the 28 MiB headroom, first come first served; **growth trigger**: when the stream's consumer has consumed half of the stream's current window since the window was last set, the window doubles, capped at 16 MiB, or grows by the remaining headroom when less than the doubling increment is left; growth is drawn from the headroom only and returns to it when the stream closes, and the reserved 1 MiB returns when the stream slot is freed; so the invariant is `Σ granted stream windows ≤ 128 MiB` at all times and a stalled or intercepted stream can never consume more than its granted window; for streamed messages, peer memory is therefore bounded by 128 MiB of DATA per connection, and a stalled stream stalls only itself; a buffered body is the flow's content and is bounded only by `body_size_limit`, which is unset by default, as upstream's is (`py:mitmproxy/addons/proxyserver.py:176-178`); the endpoint keeps the Σ in its own counter, exported to tests; **chunk hand-off**: each stream's receive buffer is a list of chunks allocated with `MAX_FRAME_SIZE` (2^17 bytes) of capacity and filled by appending, never a contiguous buffer grown by doubling; a full chunk moves to the opposite endpoint's send buffer by ownership, without copying; the partly filled tail chunk moves only when the send buffer is empty and the downstream peer can take data now (the client-facing stream and connection windows both have credit for at least one byte), and it then becomes the send buffer's head and drains as credit allows; otherwise the receiver keeps appending to the tail (an implementation may instead copy the tail's bytes into the send buffer's last chunk when that chunk is also the send buffer's head and has room, a copy of at most one chunk, after which the tail chunk is released); the hand-off is checked on two events, when DATA is appended to the tail and when the send buffer drains or the downstream stream or connection window reopens; an emptied chunk is released, not kept; so at any time a stream holds at most two partly used chunks (the receiver's tail being filled and the send buffer's head being drained, together less than 256 KiB of capacity not counted by Σ) whatever DATA frame size the origin uses: small frames sent to a stalled client fill one tail until it is full and moves as a full chunk, instead of each pinning a chunk of its own; **small streamed bodies stay prompt** (server-sent events, small chunked responses): a small DATA frame either moves at once, because the send buffer is empty and the client can take it, or waits only while it could not be sent anyway (the client has no credit, or earlier bytes of the same stream are still queued ahead of it), and the drain or window-reopen event moves it as soon as it can be sent; ## 6. Pre-mortem (three failure scenarios, with the mitigations attached to phases)

### S1 — A toolchain or dependency update breaks the build mid-port

*What happened*: Go 1.28 ships; `gvisor.dev/gvisor@go` moves to a layout the `go` branch generator mishandles (already observed for `@latest` on 1.27.1), `golang.org/x/net/http2` diverges further from std, `quic-go` 0.64 changes `quic.Stream`, `codeberg.org/miekg/dns` v0.7 changes the `RR` interface, or `go.yaml.in/yaml/v4` rc.7 changes decoding of merge keys. Three phases stall on unrelated compile errors.
*Early signals*: dependabot PRs failing; the `tip` CI job red; adapter packages growing `//nolint` comments.
*Mitigations (P0 deliverable 1 and §4)*: exact pins in `go.mod`; the five adapter packages with contract tests; CI on `stable` (blocking) and `tip` (non-blocking); `oldstable` is impossible because `go 1.27`, `encoding/json/v2` and miekg v2 (`go 1.27.0`) all require 1.27; grouped weekly dependabot; `docs/dependencies.md`.

### S2 — HTTP/1 fidelity regressions surface only in production traffic

*What happened*: the own parser mishandles a corner the upstream tests do not cover (duplicate `Content-Length` with different values, chunk extensions, trailers without `TE`, `HTTP/1.0` + `Connection: keep-alive`, `Expect: 100-continue` with a rejected request, a 204 with a body, obs-fold inside a `Set-Cookie`). Clients see hangs or truncated bodies that upstream mitmproxy handles.
*Early signals*: differential job disagreements ignored as "flaky"; bug reports mentioning specific origins; `http_fidelity` > 0 in traffic that should need no normalisation.
*Mitigations (P1 deliverables 3, 13 and §7)*: `test_read.py`/`test_assemble.py`/`test_http1.py`/`test_http.py` ported as the P1 gate; the differential harness `go:internal/difftest` on every PR touching `internal/http1`; fuzz targets seeded by hand from the vectors (upstream's fuzz tests are hypothesis strategies with no corpus, so seeds are written here); the `http_fidelity` counter from P1 (exported through OTel in P11).

### S3 — local mode on macOS/Windows/Linux stalls on artifacts and platform gates

*What happened*: the `mitmproxy_macos` wheel's `.app.tar` is an empty placeholder for unsigned builds (`rs:.github/scripts/build-macos-redirector.sh:55-58`), the chosen wheel's redirector refuses to pair with a non-mitmproxy parent, Gatekeeper/System Extension approval differs between macOS releases, the WinDivert driver (shipped signed by upstream) still needs admin and a reboot-free load, the 0.12.11 Linux redirector's eBPF program does not load on the `ubuntu-26.04` runner kernel, or the IPC schema changes in mitmproxy-rs 0.13. P6 consumes weeks without a CI-verifiable result.
*Early signals*: manual runbook attempts failing twice in a row; IPC parse errors in logs; wheel SHA-256 mismatch.
*Mitigations (P6 pre-tasks and time-boxes)*: pin a **released** 0.12.x wheel whose `.app.tar` is verified non-empty in the P6 pre-task; vendor `mitmproxy_ipc.proto` and test it against frames captured in the pre-task; keep `local` behind an explicit mode spec with a clear `unavailable_reason`; time-boxes of 3 + 4 + 5 days for the three local-mode sub-tasks (Linux packet mode, macOS stream mode, Windows packet mode) with WireGuard and TUN allowed to land alone; otherwise document local mode as "experimental, manually verified" rather than blocking the release.

## 9. ADR — Go port of mitmproxy with a hybrid core and full upstream compatibility

- **Decision**: build `mitmproxy-go` as a hybrid (sans-I/O parsers + goroutine/`net.Conn` orchestration with a single hook dispatch domain using epoch-checked re-entrancy frames and non-blocking frontend edges) port with full wire fidelity (own HTTP/1 parser, independent h2 endpoints on x/net Framer + hpack with bounded windows, own HTTP/3 framing on quic-go streams + qpack, frame-level WebSocket relay on an extended gows) and full upstream compatibility (flow format v18–v21 read / v21 write, CA layout, filter grammar, options with upstream precedence, hooks, mode specs, mitmweb API with the embedded upstream React build), covering HTTP/1–3, WebSocket, TCP, UDP, DNS, DTLS, modes regular/reverse/upstream/transparent/socks5/dns/wireguard/tun(Linux)/local(macOS, Windows and Linux via upstream redirectors), three binaries (mitmdump, mitmproxy TUI on bubbletea v2, mitmweb), Starlark scripting, Rust-derived contentviews, highlighting, process info and OpenTelemetry.
- **Drivers**: D1 asset compatibility, D2 maintainability on Go 1.27+, D3 delivery-risk control.
- **Alternatives considered**: O2 std `net/http` proxy with data-level compatibility; O3 faithful sans-I/O port; O4 fork of go-mitmproxy; an actor-goroutine dispatch variant of O1 (§2).
- **Why chosen**: O1 is the only option that satisfies the user's explicit fidelity and compatibility choices while using Go's native TLS/QUIC I/O; it reuses upstream vectors where they are cheap to port and avoids adapters where they are not.
- **Consequences**: largest code volume of the options (estimated 60–80k Go lines including tests); the h2 and h3 state machines are written here (x/net and quic-go contribute framing, HPACK/QPACK and the QUIC transport only); two coding styles that the dispatch domain and package layout keep apart; a lock discipline enforced by tests rather than types (R15); dependency on the user's gows extension; pre-1.0 dependencies (quic-go, qpack, miekg v2, yaml v4 RC) isolated behind adapters; local mode depends on upstream artifacts and manual verification; legacy TLS suites and ECH termination are not supported (R13, R14); the h2 window policy and TLS half-close (close_notify + FIN) deviate from upstream and are documented; Starlark `concurrent` is a predeclared builtin written `request = concurrent(_request)` because Starlark has no decorator syntax, runs handlers from a second, frozen module instance (top-level code runs twice per load, module-level mutable state is not shared between a concurrent handler and the main-thread hooks), gives handlers a read-only snapshot of the connection objects, is rejected on the 21 non-flow hooks other than `load`/`configure`, fails a direct Starlark call of a wrapper with a stated error where upstream returns an unawaited coroutine, and prints the script path where upstream's sync-context error prints the module repr (§1.3.1); DTLS accepts only `tls_version_*` windows that contain `TLS1_2` (P3 deliverable 4); all of these are listed in `docs/compat.md`.
- **Follow-ups** (not in this plan): `py:mitmproxy/io/compat.py` migrations for flow formats < 18; DTLS 1.0/1.3 (pion speaks 1.2 only); QUIC datagrams; Windows transparent mode (`py:mitmproxy/platform/windows.py` pydivert path); tree-sitter parity for highlighting; `mitmproxy_rs.certs` (macOS keychain install); an OpenSSL/utls-backed TLS layer for legacy suites; a static analyser for the dispatch-lock rules; kubernetes/transparent-vm how-tos.

## 10. Open items and assumptions to confirm at approval

Decided by the user during planning (recorded here so they are not re-asked): flow formats v18–v21 migrated and < 18 rejected; option precedence reproduces upstream; h2 bounded windows (100 streams, 1 MiB initial, 16 MiB max, 128 MiB granted-window budget); TLS half-close as `close_notify` + FIN; Starlark `concurrent` provided with a deep-copied flow, built per §1.3.1 (lead decision on the rev 4 review: a second frozen module instance per script, release through `addon.Concurrent`, flow hooks only; lead decisions on the rev 5 review: a predeclared `concurrent` builtin written `request = concurrent(_request)`, `GlobalReassign` off, the hook name taken from the global binding, and `script.run` a synchronous run of the script module only that rejects `concurrent` handlers whatever the depth and stops at the first error); h2 consumption defined as the downstream write for streamed messages (send-buffer bytes charged to Σ) and the body-buffer append for buffered ones, window growth by doubling after half the window is consumed, and a budget-test client that returns connection-level window (lead decisions on the rev 5 review); DTLS, TUN mode (Linux) and Linux local mode added to scope; Linux local mode follows upstream exactly (interactive `sudo echo -n` probe, `unavailable_reason` `mitmproxy is not running as root.`); TUN e2e binds curl to the device with a loopback origin and no route; h2 budget criterion uses 99 stalled streams plus one. Lead decisions on the rev 6 review: the frozen `concurrent` instance gets its own predeclared object graph, in direct mode while its top-level code runs under the dispatch lock and in worker mode afterwards, where `ctx.options` reads come from the latest atomically published immutable snapshot and writes, `ctx.master.commands.call` and `ctx.log` go through `master.Do`; h2 full chunks move to the send buffer by ownership and a partly filled tail moves only when the send buffer is empty and the client can take it, with a 1 KiB-frame rerun of the budget test; the Python `$` claim stays and P0 gains the vectors and differential rows that check it; a direct call of a `concurrent` wrapper is an error; hot reload and `remove` retire the frozen instance without waiting for in-flight workers; the sync-context error prints the script path.

Still open:
1. **Legacy TLS suites and ECH** (§1.4, R13, R14): acknowledge the loss or request the OpenSSL/utls follow-up now.
2. **Redirector wheel version**: 0.12.11 digests are recorded in §1.4; the P6 pre-task still extracts the macOS `.app.tar` and confirms the IPC schema matches the vendored 51fe2b7 proto by decoding captured frames.
3. **gows extension** is a separate task in `github.com/zchee/gows`; P3 pins its commit.
4. **DTLS versions**: pion/dtls v3 speaks DTLS 1.2 only; the single rule is in P3 deliverable 4: the `tls_version_*` options keep their TLS values (there is no `DTLS1_0` value), a window that contains `TLS1_2` is accepted and negotiates DTLS 1.2, a window with min `TLS1_3` or max `SSL3`/`TLS1`/`TLS1_1` fails that DTLS connection with the logged text. Confirm.
5. **Highlight goldens** come from the 0.12.11 wheel while the Rust pin is 51fe2b7; the P7 pre-step diffs the resolved `tree-sitter*` entries in `Cargo.lock` between the two and the plan assumes they match.
6. **Linux redirector on the runner kernel** (Critic, unscored): whether the 0.12.11 redirector's eBPF program loads on the `ubuntu-26.04` runner kernel is not verified; the P6 Linux criterion is the first check, and S3 covers the failure.
7. **Loopback destinations under Linux local mode**: not verified; the P6 criterion uses a non-loopback origin address so it does not depend on the answer.
8. **Re-attaching a persistent TUN** (Critic, unscored, asked whether a leaked descriptor makes a second attach fail with `EBUSY`): the P6 design hands wireguard-go a close-on-exec duplicate and always closes its original, and the fallback runs before any hand-over, so no descriptor leaks on the fallback; the P6 TUN criterion starts the fallback path twice to show it. If `CreateUnmonitoredTUNFromFD` fails after wrapping the duplicate, the mode start fails and the duplicate stays attached until the `os.File` finalizer closes it, so an immediate restart could still see `EBUSY`; this error path is not expected in practice and is not covered by a criterion.
9. **`IFF_VNET_HDR` on an existing persistent TUN** (Critic on rev 5, MEDIUM confidence, from memory of `drivers/net/tun.c` and not checked against source: `tun_set_iff` rewrites the feature flags on every attach, so the attach is likely accepted; the P6 lane confirms): the P6 fallback attaches with `IFF_TUN | IFF_NO_PI | IFF_VNET_HDR` (the `CreateTUN` flags, `tun/tun_linux.go:566`), while the P6 criterion pre-creates `tun0` with `ip tuntap add dev tun0 mode tun user <runner user>`, which does not set `IFF_VNET_HDR`. Whether the kernel accepts that flag mismatch when attaching to an existing device is not verified. The P6 lane either creates the test device with matching flags (`ip tuntap add ... vnet_hdr`) or confirms that the attach succeeds, and records which one in the PR.
10. **netem throughput ramp** (Critic, unscored): the proxy's stream windows start at 1 MiB and grow by doubling (P3 deliverable 1), while the direct client has a 16 MiB window from the start; on a transfer of about 1.6 s at about 160 MiB/s per hop, a ramp of several 100 ms RTTs could cost 10 to 20% and bring the P3 netem result close to the 80% floor. Mitigation: measure in the first P3 week; if the floor is missed, compare throughput after the ramp (excluding the first window doublings from both transfers) or raise the initial stream window, and record the choice in the PR.
